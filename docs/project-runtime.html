Per-Project Runtimes & the Chain of Command

Every activated project gets its own AgentCore runtime — the shared worker image with the project's S3 Files access point mounted at /mnt/files. Then: how one pulse fans out from the Team Lead through a persona orchestrator to researcher sub-agents, all sharing that one file tree.

Isolation comes from the mount, not from tool checks — there is no other project's data anywhere in the container.

1 Provisioning at project activation

Activating a project runs a two-step provision in projects.ts: create the S3 Files access point, then create the AgentCore runtime that mounts it. Both are idempotent — the project id doubles as the client token.

Provision sequence projects.ts (activate)

1
Create the access point

CreateAccessPoint rooted at /{projectId} in the S3 Files file system (itself scoped to projects/ in the artifacts bucket). POSIX uid/gid 1000, clientToken: projectId.

2
Read the runtime recipe from SSM

AGENTCORE_PROJECT_RUNTIME_CONFIG_PARAM — the infra stack publishes image URI, execution role, VPC subnets/SGs, mount path, and baseline env vars. Fetched fresh per activation.

3
Create the runtime

CreateAgentRuntime: name project_<uuid> (hyphens forbidden), the shared worker image, VPC networking, env PROJECT_ID + PROJECT_FILES_DIR, and filesystemConfigurations mounting the access point at /mnt/files.

4
CREATING → READY (async)

Typically a couple of minutes. Runs dispatched before READY fail that invocation — and are recovered by the sweeper's stale-pending redispatch.

5
Persist the ARNs

Both land on the project row: s3AccessPointArn, agentRuntimeArn. From now on, dispatch routing reads them.

Idempotent by client token

A retried activation returns the same access point and runtime instead of duplicating. If the runtime was created but the ARN never reached the project row (DB update failed) and the token has rotated out, a ConflictException is recovered by looking the runtime up by name.

Graceful degradation

No S3_FILES_FILE_SYSTEM_ID or no SSM param (local dev, minimal envs) → the helpers are no-ops, the project row keeps null ARNs, and dispatch simply falls back to the shared platform runtime. Nothing breaks — file tools return a structured "not available" error.

The deploy caveat

Deploying ResearchWorkbench/AgentCoreRuntime updates the shared runtime and the SSM recipe — which affects future project runtimes only. Existing project_* runtimes keep their activation-time worker image; there is no UpdateAgentRuntime path in the repo today. Relevant to your /ping fix: already-activated projects still run the old image until recreated.

The shell tool's containment model

projectFilesShell runs bash -c with PROJECT_FILES_DIR as cwd. Commands can leave the cwd — reachability is decided by the mount, not the tool. The child process gets a scrubbed environment so live Aurora credentials in the worker's process.env never leak into env output. On the shared runtime (no mount) the tool returns a structured error instead.

Why persona roots inherit tools

The root run's agentType is the persona's UUID — that's how descendants inherit the persona's specialist tools (resolveInheritedToolIds) and how graph writes resolve their author (resolveRunAuthor walks to the root).

The brief is the only context

Sub-agents see nothing but their plan-task spec — no lead chat, no parent transcript. That's why buildAgentBrief and every spawn brief must be self-contained: goal, constraints, budget, and the explicit instruction to persist findings to the graph (the research loop reacts only to what lands there).
