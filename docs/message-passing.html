Message Passing & Sync

How a message travels from the user to an agent and back — over two complementary channels with very different guarantees.

Durable streams are telemetry. Postgres + Electric is the truth.

1 The two channels

Live token streaming and persisted state sync are deliberately separate systems — one can die without taking the other down.

⚡ Durable streams — live telemetry

best-effort · per-run · append-only
  • One JSON stream per run at /v1/stream/run-{runId} — per-run, not per-task, because a stream's close is terminal (a reused path would 409 on the next run)
  • TaskStreamWriter appends typed events as the agent streams tokens
  • Bounded backoff (4 retries, 30s append deadline): if the streams server is dead, events are dropped with a warning — the run itself is never wedged
  • Browser tails through an authenticated proxy that verifies the run belongs to the task/project (closes cross-task IDOR)

🗄️ Electric SQL — persisted truth

authenticated shapes · long-poll · Postgres-backed
  • Four server-pinned shapes: projects, projectAgents, projectRuns, taskMessages
  • The browser's TanStack DB collections long-poll GET /sync/:shape; the API scopes the shape server-side, then proxies to Electric
  • Writes never go through Electric — they go through oRPC (or the worker) and sync back as row changes
  • Roster state (project_agent.state: working / idle / blocked) broadcasts live through the projectAgents shape

3 The rules that keep it robust

Dead streams server ≠ dead run

The durable-streams client used to retry forever with a concurrency-1 append queue — one unreachable append kept the segment promise pending, /ping reported HealthyBusy, and sessions idled to their 8-hour max, billed the whole time. Now: bounded backoff (4 retries), 30s append deadline, 15s connect deadline — a failure drops the event and warns. Postgres is the source of truth; the live stream is UX telemetry.

EOF exactly once, at terminal

closeRunStream EOFs a run's stream only when the run reaches a terminal status — so tailing consumers stop. Segment cleanup deliberately leaves it open: a yielded orchestrator resumes onto the same stream, appending across sessions.

Sub-agents multiplex

SubAgentRuntime writes a child's events onto the parent's stream writer, so the UI can render a whole run tree's activity from one tail instead of opening a stream per child.

Reads are guarded

The streams proxy verifies the requested run actually belongs to the claimed task/project before piping bytes (cross-task IDOR closed). Electric shapes are server-pinned: the client picks a shape key and a scope id, never raw SQL — and task-scoped shapes check thread ownership.

Writes never ride the sync channel

Electric is read-only fan-out. All writes go through oRPC routes (user actions) or the worker (agent results), then sync back as row changes. There is no client-side write path to conflict-resolve.

Roster state is just rows

project_agent.state flips (working / idle / blocked) happen in run-terminal.ts as guarded UPDATEs and broadcast through the projectAgents shape — the live team view is Postgres all the way down.
