Yield / Resume Orchestration

How an orchestrator run persists its state to Postgres, releases its AgentCore session, and is resumed by child completions — with every transition guarded at the database.

The parent does not stay alive waiting. It persists, exits, and is restarted when durable child state changes.

3 Why simultaneous completions cause exactly one resume

Two children finish at nearly the same instant. Both fire markRunResumable(R1). Only one can win the guarded transition.

The transition is UPDATE run SET status='pending' WHERE id=R1 AND status='waiting_on_children' RETURNING id. After the first handler flips the row to pending, the second handler's WHERE clause no longer matches — zero rows returned, so it skips the dispatch entirely. No locks, no coordinator: the row itself is the mutex.

4 The /ping fix — why sessions now actually die

Same 30-minute run segment. What differs is what happens after the invocation settles and inFlight drops to zero.

Before — timestamp advanced on every ping

Every health check returned a fresh time_of_last_update, telling AgentCore "my status just changed" forever. Idle timeout never fired; sessions lived to the 8-hour maxLifetime and got SIGTERM.

0h2h4h6h8h
■ real work (~30 min)   ▨ idle-but-billed session   ✗ SIGTERM at 8h — billed the whole time

After — timestamp omitted

The ping reports only Healthy / HealthyBusy. Once the invocation settles, the 15-minute idleRuntimeSessionTimeout runs down and the session is reaped.

0h2h4h6h8h
■ real work (~30 min)   ▨ 15-min idle window   ✓ session reaped

Long-running tools are unaffected: while any tool is executing, inFlight > 0 and the ping reports HealthyBusy, which keeps the session alive legitimately. Only sessions with nothing in flight can now idle out.

5 Recovery guarantees

The baton can be dropped anywhere — the system recovers through the same guarded transitions.

Duplicate dispatch

Guarded claimRun() only allows one pending → running transition. The losing delivery gets zero rows and drops the work silently.

Executor dies mid-segment

Leases renew every 60s. After ~180s without renewal the sweeper resets the run to pending and re-dispatches — or fails it terminally once maxAttempts is exhausted.

Lost resume notification

A parent stuck in waiting_on_children for 10 minutes with no active children is resumed by the sweeper through the same guarded markRunResumable().

Lost dispatch

A run stale in pending for 10 minutes is simply re-dispatched. Safe by construction — the guarded claim deduplicates.

Duplicate terminal writes

finishRun() only updates rows still in an active status, so a cancelled run cannot be overwritten by a late success.

Off the failure domain

The sweeper runs in a separate scheduled Lambda — a broken worker image or hung DB pool cannot take down its own crash recovery.
