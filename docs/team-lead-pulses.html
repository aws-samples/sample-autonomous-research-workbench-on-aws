Team Lead & the Three Pulses

The research loop: persona agents write observations and hypotheses to the knowledge graph, and the Team Lead is pulsed at the right moments to judge sufficiency — wait, run a contribution round, ask the owner, or conclude the project.

Pulses never advance the watermark. Only the lead's sufficiency decision does.

1 Three pulses, one entry point

All three converge on startLeadPulse() — same lazy thread creation, same busy-lead guard, same budget gate.

⏰

Scheduled heartbeat

EventBridge Scheduler fires daily per project (project-heartbeat-<id>)
fallback sweep

The safety net: catches knowledge trickling in below the sufficiency bar, missed pulses, and stuck agents. The schedule itself is the config source of truth — "stopped" just means State: DISABLED, never deleted.

🧠

Knowledge pulse

A persona's root run reaches terminal AND new knowledge exists past the watermark
5-min cooldown while agents still working

Fired from onChildTerminal → maybeKnowledgePulse. Bursts of finishes collapse into one pulse — nothing is lost because counts are cumulative until the lead acts.

🌙

Quiescence pulse

The roster just went fully idle with nothing new since the last decision
never debounced

With no runs left to finish, this may be the loop's last signal — the lead must get the chance to start another round or conclude the project.

3 Inside startLeadPulse() — the gauntlet

Every pulse — scheduled, knowledge, or quiescence — must pass four gates before a lead turn starts. Any gate can skip the pulse; a skipped pulse is retried by the next trigger or tomorrow's heartbeat, so no signal is ever lost.

1
Budget gate

checkProjectBudget() — an over-budget project pauses automated pulses (a lead turn costs money and couldn't start anything anyway). Raising the cap auto-resumes because this checks live spend, not a stamp.

2
Lazy lead-thread creation

Guarded on leadTaskId IS NULL — a concurrent first chat message and a heartbeat converge on one thread. The creation-race loser deletes its own thread and adopts the winner's.

3
Busy-lead guard — one turn at a time

If any lead run on this thread is still active, skip. This doubles as the loop's collapse valve: N personas finishing simultaneously all attempt a pulse, exactly one wins.

4
Post + dispatch (with compensation)

Insert the pulse as a taskMessage (metadata {heartbeat: true, pulse: kind} so the UI styles it as automated), createRootRun, dispatch. If enqueue throws, the run is failed and the thread released — nothing will ever pick it up otherwise.

4 The four sufficiency decisions

A pulsed lead reads the new knowledge (getNewKnowledge — read-only, watermark untouched) and picks exactly one path:

⏳

Wait

Not sufficient yet, no owner input needed → start nothing, reply briefly. The pool keeps accumulating and the next pulse reports a cumulative count.

🔄

startContributionRound

The only thing that advances the watermark. Jumps it to the newest finding's created_at_ms, then offers every idle persona the new knowledge with a triage brief — each decides for itself whether to contribute another run or pass.

✋

pauseForGuidance

Blocked on a decision only the owner can make → pauses the project, stops in-flight work, and emails the owner. Chat alone is insufficient because no user is present during a pulse.

🏁

stopHeartbeat

Objective met or nothing productive left → disables the EventBridge schedule (never deletes it) and, with concludeProject, marks the project completed — which is what actually ends all pulses: they refuse to start on non-active projects.
